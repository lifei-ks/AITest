## 2. 项目总结（面试口述版）

### 2.1 60 秒版

> 这个项目解决的是 AI 生成测试用例"不可信"的问题。常见做法是把需求丢给大模型直接生成用例，但模型会编造页面上不存在的按钮和文案，生成的步骤也没法执行。我的做法是先把被测系统的源码转成结构化事实——有哪些接口、字段有什么约束、订单状态怎么流转、页面有哪些表单和选择器——再让模型基于这些事实去写用例；模型不可用时，规则模式也能按正例/反例/边界/流转生成。用例生成后由 Playwright 真机执行，每步前后截图、整条用例录屏，断言分三层：先看 URL，再看引号里锚定的文案，实在无法验证就标 skipped，绝不因为"没报错"就算通过。最后产出覆盖矩阵、HTML 报告和脑图。整个项目最核心的设计是：确定性的部分（分析、质量闸、覆盖率、执行）绝不用 LLM，LLM 只做语言和视觉判断，而且可以整体摘除。

### 2.2 2 分钟版（补充取舍与验证）

在 60 秒版基础上补三点：

1. **为什么不用大模型直接生成 Playwright 代码**：不可控、不可审计、注入风险，且失败后无法定位是模型问题还是页面问题；结构化步骤 + 固定执行器才能做失败归因。
2. **为什么坚持纯规则做质量闸和覆盖率**：度量必须可复现。质量闸用 Linter + 100 分制 + 编辑距离去重；覆盖率区分"规划覆盖"和"执行覆盖"，执行覆盖只认 `status='passed'`，否则会出现"通过率 33%、覆盖率 100%"的自相矛盾。
3. **怎么证明不是假绿**：有单测证明"无预期结果的用例被丢弃""失败的执行不算覆盖"；e2e 里故意把预期改成不存在的文案会变 failed，改成没有引号的抽象描述会变 skipped。

## 4. 项目核心点（六个，按"难点 → 方案 → 证据 → 追问"展开）

### 核心点 1：确定性 / 不确定性分流，LLM 可整体摘除

- **难点**：AI 生成测试用例最大的问题是不可复现、不可审计、会编造。把所有环节交给模型，等于把"度量"也交给了概率。
- **做法**：
  - 纯规则层：静态分析、状态机提取、质量闸、覆盖率统计、执行器、断言；
  - LLM 层：需求 → 测试点、事实 → 用例措辞、执行截图审核；
  - 所有 LLM 调用点统一 `LlmUnavailable`（无 Key / 超时 / 429 / JSON 非法），调用方必须降级；无 Key 时全链路可用。
- **代码位置**：`app/llm/client.py`、`app/service/generation_service.py`（`_gen_llm_for_points`、`_normalize_steps`）、`app/service/requirement_service.py`（`_extract_points_llm` / `_extract_points_rule`）、`app/agent/review_agent.py`。
- **简历句式**：设计确定性/不确定性分流架构，规则层零 LLM、结果可复现；LLM 仅用于语义环节且全链路可降级，未配置 Key 时仍能跑通"分析 → 生成 → 执行 → 报告"。
- **追问预备**：LLM 挂了怎么办？→ 测试点/用例按"规则兜底"，用例按批降级（每批 5 条，失败只跳过该批），审核降级为 `unavailable` 转人工。

### 核心点 2：Spring Boot / Vue 静态解析器（事实可回溯）

- **难点**：要拿到"真实存在的元素和约束"，否则后面全是编造；而解析 Java/Vue 的常见写法坑很多。
- **做法（真实踩过的坑，面试很加分）**：
  - 类级 `@RequestMapping` 只作路径前缀，不能自身成为端点，否则会出现 `/api/orders/api/orders`；
  - 方法级注解括号可省略，`@PostMapping` 也要能解析；
  - 枚举常量必须是全大写 token，避免把构造方法名当成枚举值；
  - 实体解析排除 `Controller/Service/Repository` 等非数据模型；同一字段的多个约束（`@NotBlank` + `@Size`）要累积而不是覆盖；
  - Vue 路由**先找 `path:`，再向左找 `{` 做括号配平**，不能用 `[^{}]*` 这类正则（`meta:{}` 会打断匹配）；
  - `<el-form` 正则必须加 `(?![-\w])`，否则 `<el-form-item>` 会被当成表单。
- **代码位置**：`app/analyzer/spring.py`、`app/analyzer/vue.py`、`tests/test_analyzer_regression.py`（回归测试锁定上述坑）。
- **简历句式**：实现 Spring Boot/Vue 静态解析器，产出端点、字段约束、枚举、业务规则、表单与选择器等结构化事实，每条事实可回溯到 `file:line`。
- **追问预备**：为什么不用 AST/ANTLR？→ 跨语言成本高，项目范围是常见写法；用正则 + 括号配平 + 回归测试保证可预期，并在 README 明确"启发式、非语法级精确"。

### 核心点 3：状态机提取 + BFS 流转用例

- **难点**：状态流转不能靠猜。标了 `verified` 却找不到源码依据，整套覆盖率和用例可信度都会崩。
- **做法**：
  - 找状态枚举 → states；
  - 找 `setStatus(X)` 写入点，**有写入点才 `verified=true`**；
  - 向上找方法边界，由方法名推断 trigger（`pay → 支付`）；
  - 守卫语义用"是否以 `!` 开头"做异或：`if(!X) throw` → 来源态 = {X}；`if(X) throw` → 来源态 = 全集 − X；
  - 支持排除语义：`if ("SHIPPED".equals(s) || "COMPLETED".equals(s)) throw` → 来源态排除这两个；
  - 写初始态的 `setStatus(CREATED)` 视为对象初始化，不生成流转；
  - 用 BFS 算"从初始态到目标态的最短推进路径"，生成流转用例时反查真实按钮文案（支付 → 发货）作为前置步骤。
- **代码位置**：`app/agent/state_machine_agent.py`（`extract_state_machines`、`bfs_paths`）、`app/agent/test_generator_agent.py`（`_gen_state`）。
- **简历句式**：从 `setStatus` 写入点与守卫条件反推状态机（含否定与排除语义），9 条转换全部带源码证据；用 BFS 计算最短推进路径，自动生成"前置推进 + 触发动作"的流转用例。
- **追问预备**：怎么防止乱标 verified？→ 唯一判据是写入点；找不到就 false，不做推断；单测覆盖否定/排除/证据行号。

### 核心点 4：Playwright 执行器与三层断言（"不假绿"的落地点）

- **难点**：UI 自动化最容易"假绿"——元素没找到但没抛异常、断言只匹配到页面原本就有的文案、按钮文案被组件库插了空格。
- **做法**：
  - `uiSelector` 类型映射：`route / placeholder / text / label / role / testid / css / xpath`；输入框**禁用 `text=`**，用 `[placeholder="..."]`；
  - 五级兜底（第 5 级是"选不到"的失败处理）：① `uiSelector` 精确匹配 → ② `target` 文本在 `button/a/[role=button]` → ③ `target` 全页文本（排除 option/script/style）→ ④ `normalize-space(.)` XPath（解决 Element Plus 把"登录"渲染成"登 录"）→ ⑤ 全部失败：`failed` + `SELECTOR_NOT_FOUND` + 保留尝试链；
  - 三层断言：URL 命中 → 引号锚点文案全部命中 → 都没有就诚实 `skipped`；**skipped 不算通过**，报告里单独统计；
  - 6 类失败归因：`SELECTOR_NOT_FOUND / ASSERT_FAILED / NAVIGATION_FAILED / TIMEOUT / CASE_INVALID / ENV_ERROR`；
  - 每步前后截图、每条用例 WebM 录屏；执行前强制写 `test_case_snapshot`，用例改了删了历史仍可复现；
  - 证据文件接口做路径穿越校验（`realpath` 必须落在 `outputs/` 下）。
- **代码位置**：`app/agent/execution_agent.py`、`app/service/execution_service.py`、`app/routers/executions.py`（`_safe_file`）。
- **简历句式**：基于 Playwright 实现可回溯执行器，多类型选择器映射 + 五级兜底 + 三层断言，明确区分 passed/failed/skipped，逐步截图与录屏留证；e2e 实测 13 条用例通过率 92%、71 张截图、13 段录屏。
- **追问预备（真实的 bug 故事）**：
  1. 中文角括号 `「」`（U+300C/U+300D）与英文弯引号写混，导致断言锚点全提不到、全部 skipped —— 说明"通过率突然变高"要先怀疑断言；
  2. 提交后 500ms 才跳转列表页，断言等不及 → `state_assert` 前加等待；
  3. 边界用例漏填其他必填字段 → 改成从后端 `@NotBlank` 推断必填；
  4. 状态断言用"状态 label"会假绿（初始数据里本来就有"已支付"订单）→ 改用"操作成功文案"。

### 核心点 5：三道质量闸 + 覆盖矩阵双口径

- **难点**：生成 100 条不可执行的用例没有价值；覆盖率口径错了会出现"通过率低但覆盖率 100%"。
- **做法**：
  - 闸 1 `UiLanguageLinter`：拦截"调用接口 / 发送请求 / 验证数据库 / 检查返回值"、"无 uiSelector 的抽象动作"、"页面显示正常/符合预期"这类不可验证断言；
  - 闸 2 打分：100 起，lintIssue 每条 −8（上限 −40），无选择器步骤 −10，`coverageRefs` 全空 −10，步骤 >15 −10，**无 expectedResults 直接丢弃**，<40 丢弃；
  - 闸 3 去重：标题 + 首步骤归一化编辑距离，阈值 0.95（原方案 0.85 会误杀"收货人为空 / 手机号为空"这类合法不同用例——这是有意识的取舍）；
  - 覆盖矩阵：规划覆盖（有用例引用）vs 执行覆盖（**有执行记录且该次执行 `passed`**），rate 一律 0~1；
  - 单测 `test_coverage_executed_filters_passed` 锁定"失败不算覆盖"。
- **代码位置**：`app/agent/quality_gate.py`、`app/service/coverage_service.py`、`tests/test_mindmap.py`、`tests/test_quality_gate.py`。
- **简历句式**：设计三道质量闸与规划/执行双口径覆盖矩阵，执行覆盖仅统计 passed 记录，避免"通过率与覆盖率自相矛盾"，并用单测固化该语义。
- **追问预备**：权重依据？→ 先保证"可执行 + 有预期"两条硬门槛，再扣分；去重阈值用误杀案例调过。

### 核心点 6：LLM 两阶段生成 + 多模态截图审核闭环

- **难点**：长 JSON 会被截断/夹带解释；一次生成几十条容易"串味"（张冠李戴）；截图审核很容易被模型的自报置信度误导。
- **做法**：
  - 需求版本 → 测试点：LLM 优先（最多 20 条，带 category/priority/pageRoute/fields/expected/confidence），失败降级为 PRD 行级规则抽取；
  - 测试点 → 用例：**每批 5 条**，要求回填 `testPointId`，服务端校验 id 必须属于本批，防止跨批串味；单批失败只跳过该批、由规则模式补足；LLM 漏掉首步导航时自动补 `route` 步骤；步骤类型白名单 + 字段截断（`_normalize_steps`）；
  - JSON 健壮性：JSON mode + 去 markdown 包裹 + 尾逗号修复 + 截断数组闭合（`LlmClient._parse_json`）；
  - 截图审核：挑选最多 6 张关键截图（失败步骤前后 → 最后一步 → 断言步骤 → 第一步），base64 走多模态接口，要求输出 `verdict / reason / 逐图 analysis / issues.bbox`；bbox 兼容 0~1 与像素坐标（直接读 PNG 头换算，不依赖 Pillow），越界裁剪、过小丢弃；
  - 审核结论：`suspect / unavailable` → `needs_review` 人工复核；`ok` 但存在选择器/环境/超时等硬错误 → 仍转人工，避免"没跑起来却判通过"；
  - **不采信模型自报 confidence**（无校准依据），直接废弃该字段，避免伪量化。
- **代码位置**：`app/agent/review_agent.py`、`app/service/execution_service.py`（`_decide_status`）、`app/llm/client.py`。
- **简历句式**：实现"需求 → 测试点 → 用例"两阶段 LLM 生成（JSON mode + 分批 + 单批降级），并接入多模态截图审核，输出结论、逐图分析与问题坐标，suspect 自动转人工复核，形成"生成-执行-审核-复核"闭环。
- **追问预备**：幻觉怎么控？→ 只用代码事实做上下文 + 提示词硬约束（禁 api_call、必须真实路由/placeholder）+ 服务端校验 + 质量闸 + 执行器兜底；为什么不直接执行模型生成的代码？→ 安全与可定位性。

> 如果时间只够讲 3 个点：**核心点 1（架构取舍）+ 4（执行与不假绿）+ 5（覆盖率口径）**。这三个最能区分"用过 AI"和"做过测试平台"。

## 8. 高频追问与参考回答

**Q1：你的用例和直接用 ChatGPT 生成有什么区别？**
A：三点。第一，生成前先做代码静态分析，把端点、字段约束、状态机、表单选择器作为事实注入提示词，模型只能引用真实元素；第二，输出是结构化步骤（类型/选择器/输入值/预期），能被执行器消费，不是自然语言；第三，生成后有质量闸和执行验证，失败会归因，验证不了标 skipped。

**Q2：怎么保证覆盖率不是刷出来的？**
A：两个口径分开算。规划覆盖看有没有用例引用该端点/转换；执行覆盖必须该用例有执行记录且 `status='passed'`。失败不算覆盖，skipped 也不算。有单测专门造一条 failed 记录验证覆盖率不涨。

**Q3：LLM 生成的用例执行通过率多少？**
A：规则模式 e2e 是 13 条 92%；LLM 模式需要配置 Key，README 记录过一次 18 条生成、13 条 LLM 产出。具体数字我会现场跑给你看，不同模型波动较大。

**Q4：为什么不用 Celery/Redis？**
A：范围控制。生成和执行都是单机任务，`asyncio.create_task` + 线程 + 队列足够；批量执行刻意串行，避免多个浏览器抢资源、录屏对不齐。引入队列会显著增加部署复杂度，但对这个项目没有收益。

**Q5：状态机的 verified 会不会造假？**
A：唯一判据是找到 `setStatus(X)` 的写入点，并记录 `file#line`；守卫条件用 `!` 的异或语义推导来源态；写初始态不算流转。找不到写入点就是 false，不做推断。

**Q6：Element Plus 的按钮为什么点不到？**
A：两字按钮会被渲染成"登 录"（中间插空格），`has-text` 匹配不到；兜底链最后一级用 `normalize-space(.)` 的 XPath，忽略空白后匹配。

**Q7：截图审核的 bbox 准吗？**
A：模型给的是估算坐标，可能偏移。后端做了三件事：兼容 0~1 与像素坐标（读 PNG 头换算）、裁剪到图内、过小丢弃；前端只做红框提示，不参与通过/失败判定。

**Q8：这个项目最大的技术难点是什么？**
A：不是调模型，是"让结论可信"。三个具体难点：源码事实提取的鲁棒性（类级前缀、Vue 路由括号配平、表单正则）、执行断言的防假绿（三层断言 + skipped 语义）、度量自洽（覆盖率的 passed 过滤）。每个都踩过坑并有测试兜底。
