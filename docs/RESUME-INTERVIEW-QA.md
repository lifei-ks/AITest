# AITest 简历项目面试问答

> 这份文档按你简历里的四段描述逐条准备。
>
> 回答原则：**先给结论，再给原因和取舍，最后给真实结果**。不要背成长篇大论，每道题控制在 30～60 秒。

---

## 0. 先修正简历里的 3 个高风险表述

面试官最喜欢抓“过度包装”。这三处建议先改，否则很容易被追问到答不上来。

### 0.1 “基于 AI 解析需求文档与源码”

**风险**：源码分析并没有用大模型，而是规则解析。面试官问“源码解析用的什么模型/怎么处理 AST”，会露馅。

**建议改成**：

> 基于 LLM 解析需求文档，结合规则静态分析前后端源码，提取接口、字段约束及状态机……

**回答口径**：

> 需求文档是自然语言，用 LLM 做语义提取；源码是结构化代码，用规则解析更稳定、可复现，也避免把源码上传给模型。两者产出统一的代码事实，再交给生成层。

### 0.2 “VLM 输出审核结论、置信度”

**风险**：当前视觉审核输出的是 `ok / suspect / unavailable`、原因、逐图分析和异常区域坐标，**不输出置信度**。代码里明确废弃了模型自报置信度，理由是“没有校准依据，不参与判定”。如果面试官问“置信度怎么校准、阈值多少”，很难圆。

**建议改成**：

> 输出审核结论、异常描述与异常区域坐标，可疑结果转入人工复核。

**如果已经被问“置信度”**，这样答：

> 早期确实记录过模型自报 confidence，但后来发现模型自报置信度没有校准，不能作为判定依据，所以废弃了。现在用三态结论 `ok / suspect / unavailable`，加上证据不足一律 suspect、可疑转人工复核。结果分析模块会输出根因判断的置信度，但它不参与执行通过/失败的判定。

### 0.3 “AI 用例生成”

**风险**：听起来像所有用例都由大模型生成。实际是 LLM 优先、规则兜底，真实 V3 用例里规则占比不低。

**建议口径**：

> 生成策略是 LLM 优先、规则兜底。规则保证没有 Key 也能跑、结果可复现；LLM 负责语义增强。每条用例都标注来源，用户能区分。

## 1. 开场类

### Q1：请先介绍一下这个项目（2 分钟）

> AITest 是一个面向 Web 业务系统的自动化测试生成与执行平台。
>
> 它解决两个问题：手工写 UI 用例成本高、和代码变更脱节；纯 LLM 生成又不可复现、容易编造选择器和预期。
>
> 我的方案是把系统分成确定性内核和 LLM 增强两层。底层用规则静态分析 Spring 和 Vue 源码，得到接口、字段约束、页面路由、选择器和状态机这些代码事实；再生成测试点和结构化用例，经过质量闸过滤复合场景、多输入和不可验证断言；最后用 Playwright 在真实浏览器执行，采集截图和录像。
>
> LLM 负责需求解析、用例参数和审核建议，但**不决定执行是否通过**。确定性失败不能被 AI 改成通过，证据不足就标 skipped 或待复核。
>
> 平台还提供一键 Pipeline，从代码分析、测试点、用例生成、审核、执行到报告共 7 个阶段，每阶段落库、可追踪。真实订单系统 V3 上，30 条用例从 20 条失败修到 25 条通过、5 条待复核、0 条失败，后端 144 个测试通过。

### Q2：为什么要做这个项目？解决什么痛点？

> 三个痛点：
>
> 第一，手工写 UI 用例重复劳动多，页面一改就要维护一堆选择器。
>
> 第二，纯 LLM 生成看起来快，但不可复现、会编造页面元素，测试结果不可信。
>
> 第三，很多平台只生成不执行，或者执行了只给一个红绿，没有证据和覆盖口径。
>
> 所以我想做的是“从代码事实到真实执行证据”的闭环：生成有约束、执行有证据、结果可归因、覆盖有口径。

### Q3：这个项目是你独立做的吗？你负责哪部分？

> 如果是独立项目：从静态分析、生成器、执行器、Pipeline、前端到测试都是我做的。
>
> 如果被追问细节，按模块说：分析器负责 Spring/Vue 事实提取；Agent 层负责测试点和用例生成；质量闸和执行器是确定性内核；前端负责生成进度、用例管理和执行证据展示。我重点投入在生成质量、执行稳定性和真实故障归因上。

### Q4：这个项目最难的点是什么？

> 最难的不是接大模型，而是**让生成结果真的能执行、且执行结果可信**。
>
> 举一个真实例子：V3 订单系统 30 条用例一开始 20 条失败。我先按错误分类统计，发现大部分不是被测系统坏了，而是生成器假设错了：列表页点了“提交”、Element Plus 下拉框定位不到、状态触发词“支付”误命中“待支付”。
>
> 我最后是回到生成器和执行器修页面分支、选择器和匹配逻辑，而不是逐条改用例。修完 0 失败，剩下 5 条我主动标待复核，因为执行器确实没有能力证明批量取消和统计变化。

### Q5：用一句话概括这个项目的价值？

> 它不是“让 AI 写测试”，而是“用代码事实约束 AI，用真实执行证据兜底”，核心价值是**可信和可复现**。

## 2. 架构与流程

### Q6：整体架构怎么分层？

> 四层：
>
> 1. 输入层：需求文档、源码目录、被测站点 URL。
> 2. 确定性内核：静态分析、状态机、质量闸、数量改写、Playwright 执行器、覆盖统计。
> 3. LLM Agents：测试点、用例参数、审核建议、截图语义、结果分析，全部可选、可降级。
> 4. 编排与展示：FastAPI 服务、Pipeline、Vue 前端、报告/脑图。
>
> 关键边界是：**执行是否通过由确定性内核决定，LLM 只做语义增强和人工复核建议。**

### Q7：一次完整的数据流是怎样的？

> 需求文档 + 源码 → 代码分析得到接口/字段/页面/状态机 → 测试点 → 结构化用例 → 质量闸 → 审核 → Playwright 执行 → 截图/录像/步骤 → 结果状态机 + VLM 审核 → 覆盖矩阵和报告。
>
> 落库上大致是：`code_analyses`、`state_machines` → `requirements`、`test_points` → `test_cases`、`case_generations` → `workflow_cases` → `execution_records`、`execution_steps` → `execution_reviews`。

### Q8：为什么规则 + LLM，而不是全规则或全 LLM？

> 全规则可复现但语义不够灵活，复杂需求写不出自然场景；全 LLM 灵活但不可复现、会幻觉、不可审计。
>
> 我的取舍是：**规则保底，LLM 增强**。规则保证没有 Key 也能跑、结果稳定；LLM 在代码事实约束下补语义。LLM 失败自动降级，用户能看到 fallbackReason 和 source。

### Q9：Pipeline 是怎么串起来的？

> 7 个阶段：代码分析 → 测试点 → 用例生成 → 用例审核与修订 → 自动执行 → 结果分析 → 报告。
>
> 每个阶段落一条 `WorkflowStage`，记录状态、耗时、输入输出摘要和错误。审核阶段只有 `review_status=pass` 且 `automation_status=automated` 的用例才进入执行。阶段失败会保留现场，便于定位和恢复。

### Q10：生成版本是怎么隔离的？

> 每次生成创建一个只读 `CaseGeneration` 快照，实时用例始终指向最新。页面可以切“实时用例（最新）”或历史版本。
>
> 重新生成不会把多次结果合并到一起，也不会因为用例被替换就丢失历史。早期没有版本记录的用例，首次查看时自动归档成 legacy 版本。

## 3. 源码静态分析与需求解析

### Q11：源码静态分析具体怎么做的？用了 AST 还是正则？

> 目前是规则解析，不是 AST，也没有把源码交给大模型。
>
> `scanner` 按扩展名扫描文件，Spring 分析器解析类级/方法级映射注解、参数约束、实体字段和抛出的业务异常；Vue 分析器解析模板里的表单、字段、placeholder、按钮文案和选择器。最终映射到统一的 `BackendResult / FrontendResult / StateMachine`。
>
> 为什么不用 AST：项目要快速支持多技术栈、多写法，规则解析实现成本低、结果稳定；代价是复杂语法可能漏报，所以分析结果只是“可用事实”，最终还有质量闸和审核兜底。

### Q12：接口、字段约束具体怎么提取？

> 接口：识别 `@GetMapping/@PostMapping/...`，结合类级 `@RequestMapping` 前缀拼出完整路径；参数注解和 `@PathVariable/@RequestParam` 决定参数结构。
>
> 字段约束：解析实体字段上的 `@NotBlank/@NotNull/@Size/@Pattern/@DecimalMin` 等，转成 `FieldConstraint`；前端再解析 `el-form` 的字段和 placeholder。
>
> 前后端事实交叉使用：后端约束判断必填/长度，前端事实判断页面怎么填、按钮叫什么。

### Q13：状态机是怎么提取的？能举个例子吗？

> 从 Controller/Service 代码里找状态赋值和守卫条件。比如订单支付：找到 `order.setStatus(PAID)`，再往前找 `if (status != CREATED) throw ...`，得到 `CREATED → PAID`，触发词是“支付”。
>
> 这里踩过一个真实的坑：守卫条件是 `status != CREATED`，并且用的是 `continue/return` 而不是 `throw`。早期只识别 `throw`，批量取消被拆成 5 条错误转换。修复后识别 `throw/continue/return/break`，同时把否定条件归一成单一源状态，`batchCancel` 只产出一条 `CREATED → CANCELLED`。

### Q14：Vue 页面元素怎么解析？

> 解析 `.vue` 模板里的 `el-form`、`el-form-item`、`el-input`、`el-select`、按钮等，提取字段 label、prop、placeholder、按钮文案和页面路由。
>
> 这一步的产物直接约束 LLM 能引用哪些 placeholder/按钮；LLM 不允许用 css/xpath 发明选择器。

### Q15：分析器漏了接口/字段怎么办？

> 平台的原则是“宁可不生成，也不编造”。
>
> 静态分析漏了，生成层就缺少事实，质量闸和审核会发现选择器/锚点不在源码事实中，标记为风险或拒绝；执行阶段如果找不到元素，会归为 `SELECTOR_NOT_FOUND`，而不是当成应用 bug。
>
> 代价是覆盖率会偏保守；这是有意的取舍，因为测试平台最怕假绿。

### Q16：如果要支持 React 或别的语言，怎么扩展？

> 分析器是插件式的：`scanner` 给文件列表，分析器输出统一的 `BackendResult/FrontendResult`。加 React 就是新增一个 analyzer，把页面、表单、选择器映射到同一套模型；生成器和执行器不需要改。
>
> 接口层再加对应的注解解析即可。真正的工作量在“不同框架的页面结构差异”，而不是执行器。

## 4. AI 用例生成

### Q17：Prompt 是怎么设计的？

> 不是把需求和代码整段丢给模型，而是给它“受约束的事实包”：
>
> - 页面路由、字段、placeholder、必填约束
> - 真实选择器类型
> - 真实接口、状态机、页面文案
>
> 同时写硬性要求：一个测试点一个输入场景、一个可观察预期；只允许 route/placeholder/text/label/role/testid；禁止 css/xpath；禁止编造页面没有的按钮和文案；复合场景要拆成多条用例。

### Q18：怎么保证 LLM 输出一定能执行？

> 四道校验：
>
> 1. 结构校验：必须是 JSON，必须有 `testPointId`、步骤、预期。
> 2. 选择器校验：只允许可验证的选择器类型，css/xpath 直接拒收。
> 3. 语义校验：复合预期、多输入、锚点数量、必填字段。
> 4. 兜底：不合法就丢弃该条，让规则生成器补这个测试点。
>
> 平台不会“尽量修补”一个明显不可执行的用例。

### Q19：LLM 幻觉怎么防？

> 三层：
>
> 第一层，输入约束：只给它代码事实，不给它自由发挥的空间。
>
> 第二层，输出约束：选择器类型白名单、锚点数量、输入数量、必填字段、复合预期。
>
> 第三层，执行约束：找不到元素就是 `SELECTOR_NOT_FOUND`，断言不命中就是 `ASSERT_FAILED`，验证不了就是 skipped，不会因为模型说“应该通过”就通过。

### Q20：LLM 优先、规则兜底具体怎么实现？

> 生成入口支持 `rule / llm / auto`。`auto` 先调 LLM，按测试点分批生成；模型不可用、输出非法、超时或没有覆盖某个测试点时，剩余测试点交给规则生成器，并记录 `fallbackReason`。
>
> 每条用例有 `source=ai/rule`，前端会显示来源，用户能区分。

### Q21：质量评分怎么算？

> 起步 100 分：
>
> - 每个 lint 问题 -8，最多扣 40；
> - 每个缺少 uiSelector 的步骤 -10；
> - coverageRefs 全空 -10；
> - 步骤超过 15 步 -10；
> - 低于 40 分直接丢弃。
>
> 硬门槛还有：没有预期、复合预期、同一字段多个输入，直接丢，不进入打分。

### Q22：相似度去重阈值为什么是 0.95？

> 去重指纹是“标题 + 全部步骤 + 预期”归一化后的相似度。阈值 0.85 会误杀“收货人为空”和“手机号为空”这种合法不同用例，因为它们标题结构很像；0.95 只去掉几乎完全一致的重复。
>
> 另外，同一测试点拆出的合法/越界用例预期不同，不参与去重；不同测试点的用例也不会因为步骤相似被合并，避免覆盖点丢失。

### Q23：为什么坚持“一个测试点一个场景”？

> 因为证据只保留最后一次输入。如果一条用例先填 20 字验证成功、再改 21 字验证报错，失败时无法判断是哪个场景出的问题，截图也只拍到最后一次。
>
> 所以质量闸会把复合预期和同字段多输入直接拆掉/丢弃，保证失败可归因。

### Q24：动态数据怎么处理？比如列表总数一直变。

> 用 capture 读取运行时基线，再断言 `${base_count+1}`，而不是写死“共 5 条”。
>
> 前提是前面有创建/新增动作、能确定唯一列表路由、只有一个总数断言。没有创建动作、路由不确定、多个总数断言时，宁可丢弃用例，也不生成看起来动态但实际不可执行的步骤。

### Q25：为什么不能直接断言固定总数？

> 测试数据是持久化的，共享环境里总数随时会变。固定总数会让用例在脏数据环境必然失败，而且失败原因不是业务 bug，是测试数据问题。
>
> 平台的选择是：能建立基线就动态断言，建立不了就改用唯一订单号/收货人，再不行就丢弃并提示。

## 5. Playwright UI 自动化

### Q26：为什么选 Playwright，不选 Selenium？

> Playwright 自带自动等待、浏览器上下文、录屏、多浏览器，API 更现代；执行器需要稳定定位和证据采集，Playwright 更合适。
>
> Selenium 生态更大，但等待、录屏、上下文隔离要自己补很多。这个项目是 Python 技术栈，Playwright 的 Python 绑定也够用。

### Q27：多级元素定位具体有哪几级？

> 五级兜底：
>
> 1. `uiSelector` 精确匹配，比如 placeholder、label、role、testid。
> 2. 文本按钮/链接/role=button。
> 3. Element Plus 下拉选项。
> 4. 页面任意文本（排除 option/script/style）。
> 5. normalize-space XPath，处理“登 录”这种两字按钮被拆开的情况。
>
> 这样同一个用例在不同渲染细节下更容易找到元素。

### Q28：分层断言怎么做的？

> 三层：
>
> 1. URL 断言：预期里有路由/跳转，检查当前 URL。
> 2. 文本锚点断言：预期里的「」文案必须在页面文本里出现。
> 3. 无法验证时返回 `skipped`，并说明“没有可验证的断言锚点”。
>
> 核心原则是：**没报错不等于通过**。验证不了就诚实标跳过。

### Q29：UI 自动化不稳定，你怎么处理？

> 分几层：
>
> - 定位用多级兜底，必要时等待可见；
> - 断言用稳定文案锚点，不用整页文本；
> - 动态数据用 capture，不写死；
> - 失败按 6 类错误归因：元素找不到、断言失败、导航失败、超时、用例无效、环境错误；
> - 对确实无法稳定验证的场景，标 skipped/待复核，而不是靠重试刷绿。
>
> 也要承认：当前定位是立即探测，慢渲染可能假红；`body` 兜底也可能误点外层容器，这是下一步要改的。

### Q30：截图和录像怎么采集？

> Playwright 的 context 开启 `record_video_dir` 录 WebM；每个步骤前后各截一张图，失败时截当前页面。步骤记录里保存 action、target、selector、result、error、截图路径。
>
> 执行记录还会保存用例完整快照，用例后来被修改/删除，历史执行仍然能回看。

### Q31：6 类错误分类有什么价值？

> 可以区分“生成问题、应用问题、环境问题”。比如 `SELECTOR_NOT_FOUND` 多半是生成器选择器错了或页面变了；`ASSERT_FAILED` 可能是业务 bug；`ENV_ERROR` 是浏览器/驱动问题。
>
> 有了分类才能做批量归因，而不是逐条看日志。

### Q32：执行器目前不支持什么？

> 表格行勾选、复杂拖拽、文件上传、iframe、Canvas，以及直接验证接口契约。
>
> 这些场景现在会做 UI 入口冒烟或标待复核，不会伪造成通过。下一步可以加 API 步骤和表格操作能力。

## 6. 多模态 AI 审核

### Q33：截图是怎么交给 VLM 的？

> 从执行步骤里挑关键截图，转成 base64 data URL，和用例预期、步骤记录、目标地址一起组成多模态 prompt，发给配置好的视觉模型。
>
> 只把相关截图给模型，不是把整段录像丢进去，控制成本和延迟。

### Q34：VLM 输出什么结构？

> 汇总结论 `verdict=ok/suspect/unavailable`、中文原因、逐图分析、问题列表；每个问题可以带步骤号、问题描述和归一化坐标 `bbox=[x1,y1,x2,y2]`。
>
> 前端用 bbox 在截图上画红框，方便人工定位。

### Q35：AI 能直接判定用例通过吗？

> 不能。执行结果先由确定性执行器判定；AI 只能：
>
> - 原始 passed，AI 觉得有问题 → 降为 `needs_review`；
> - 原始 skipped，AI 有足够证据 → 可以确认 passed；
> - 原始 failed/cancelled → 保持失败，AI 不能洗成通过。
>
> 这是平台的底线：模型不能覆盖确定性事实。

### Q36：简历里写了“置信度”，这个置信度怎么来的？阈值多少？

> （这题很可能被追问，建议先改简历。）
>
> 早期确实记录过模型自报的 confidence，但后来发现它没有校准依据，不能作为判定阈值，所以废弃了。现在审核只输出三态结论和证据，证据不足一律 suspect，转人工复核。
>
> 结果分析模块会输出根因判断的置信度，但那是给报告排序/展示用的，不参与执行通过/失败判定。

### Q37：异常区域坐标怎么用？

> VLM 返回归一化 bbox，后端校验坐标范围，前端按图片尺寸换算成像素画红框；同时把问题描述、步骤号、截图关联起来，人工复核时可以直接定位到异常区域。

### Q38：VLM 误判/幻觉怎么办？

> 四个措施：
>
> 1. Prompt 明确“证据不足判 suspect，不要放过”；
> 2. 模型结论只能降级，不能升级 failed；
> 3. 返回结构非法/调用失败 → `unavailable`，不影响确定性结果；
> 4. 可疑结果转人工复核，保留截图和 bbox 作为证据。

### Q39：VLM 审核成本/延迟怎么控制？

> 只挑关键截图，不传录像；限制图片数量和 token；审核是执行后的增强步骤，失败/超时降级为 unavailable，不阻塞执行结论。
>
> 规模上来可以把审核做成异步队列，不占执行线程。

## 7. 覆盖、报告与指标

### Q40：覆盖矩阵怎么算？

> 分两个口径：
>
> - 规划覆盖：用例的 `coverageRefs` 是否引用真实接口、已验证的状态转换、业务规则。
> - 执行成功覆盖：只统计 `status=passed` 的执行记录，而且只算当前实时用例。
>
> 按模块输出用例数、通过、失败、待复核、未执行和通过率。

### Q41：为什么执行成功覆盖只算当前实时用例的 passed？

> 因为旧版本用例可能已经被替换，失败执行也不能算覆盖。如果把历史执行都算进去，覆盖率会虚高。
>
> 这个口径更严格，但更可信。

### Q42：报告和脑图有什么？

> HTML 报告包含执行统计、通过率、失败分类、每条用例的步骤、截图、错误信息、覆盖矩阵和执行成功矩阵；脑图支持在线预览和 XMind/Markdown 导出。

### Q43：你怎么证明这个平台有效？通过率多少？

> 后端 144 个测试通过；真实订单系统 V3 上，30 条用例执行结果是 25 通过、5 待复核、0 失败。修复前是 20 条失败。
>
> 我不会只报通过率。还会报待复核比例和覆盖口径，因为通过率可以通过少生成、弱断言刷高。

## 8. 工程化与取舍

### Q44：测试怎么做的？

> 后端 144 个 pytest，覆盖 API、分析器、生成器、质量闸、状态机、执行一致性、工作流；关键生成行为有回归测试，比如列表筛选点“查询”、金额解析、Element Plus 下拉选择器、六状态断言、两位小数 capture。
>
> 前端目前只有构建校验，没有单元测试，这是已知短板。

### Q45：为什么默认 SQLite，又支持 MySQL？

> 本地/演示零配置，SQLite 足够；生产多进程/并发写需要 MySQL。
>
> 代码里踩过 MySQL collation、连接断开、TEXT 上限的坑，所以做了兼容处理和显式提交/释放连接。

### Q46：并发和规模怎么扩展？

> 当前批量执行是串行、线程内跑 Playwright，适合单机。规模上来要：任务队列、执行 worker 池、浏览器池、取消状态持久化、MySQL 连接池和心跳回收。
>
> 现在也有已知问题：服务重启后执行记录可能停在 running，需要启动时回收。

### Q47：安全上有什么问题？

> 当前是本地单用户工具，没有账号体系。代码审查发现报告模板未转义、项目名可拼出路径穿越、API 未校验项目归属等问题。生产化要加认证授权、报告转义、目录边界和 Key 加密。
>
> 我不会说“没有安全问题”，而是知道边界在哪。

### Q48：如果给你两周，你先改什么？

> 第一周修两个 P0：用例编辑保存丢字段、Pipeline 必填字段审核过严；再做数据一致性：执行证据按 execution_id 隔离、版本回滚、删除级联。
>
> 第二周做安全收口：报告转义、证据目录、API 归属校验；然后补执行器的接口步骤和表格勾选，最后加前端测试和 CI。

### Q49：为什么把增量分析删了？

> 多期需求差异分析维护成本高，当前场景不需要；删除后保留了生成版本快照，历史数据不破坏，旧表不主动 DROP。
>
> 这件事我的收获是：知道什么时候删功能，也是工程判断。

## 9. 行为面试 / 难点复盘

### Q50：讲一个你解决过的最难的问题（STAR）

> **S：** V3 订单系统 30 条用例，执行 20 条失败。
>
> **T：** 需要判断是应用 bug、生成器问题还是执行器问题，并修到可交付。
>
> **A：** 先按错误分类统计：SELECTOR_NOT_FOUND 9、ENV_ERROR 8、ASSERT_FAILED 2、TIMEOUT 1。定位到四个根因：列表页点“提交”、Element Plus 下拉定位错误、金额解析把“闭区间”误判成区间、状态触发词“支付”命中“待支付”。然后改生成器的页面分支、选择器和匹配逻辑，增加 LLM 不支持步骤的拒收，执行器补下拉选项兜底。
>
> **R：** 0 失败，25 通过，5 待复核。剩下 5 条是执行器确实没有表格勾选/数据变更能力，我没有伪造成通过。

### Q51：AI 生成出错的一次经历？

> LLM 生成过“勾选待支付订单复选框”“通过 API 注入不存在 ID”这类执行器不支持的步骤，导致 SELECTOR_NOT_FOUND/TIMEOUT。
>
> 我的处理不是逐条删，而是在生成层加确定性拒收：动作里出现勾选/复选框/API/注入就直接拒收，交给规则兜底；同时更新 prompt 明确禁止。这样同类问题不会再进来。

### Q52：你和别人有分歧时怎么处理？

> 比如“AI 能不能直接判通过”。我的立场是执行事实不能交给模型，模型只能降级/建议人工复核。理由是测试平台的第一诉求是可信，模型自报置信度没有校准。
>
> 最后的方案是折中：模型可以做语义审核，但确定性 failed 不能改成 passed，passed 只能降为待复核。

### Q53：如果重做一次，你会怎么改？

> 我会更早把“用例契约”和“执行证据隔离”定死：前后端统一 camelCase、证据目录按 execution_id、审核必填字段按页面。这样能少走很多返工。
>
> 另外会把接口测试能力放进执行器，而不是只用 UI 冒烟覆盖批量取消这类场景。

## 11. 红线：不要说的话

- 不要说“AI 全自动生成并判断通过”——平台明确不让模型判绿。
- 不要说“通过率 100%”——真实是 25 通过 + 5 待复核。
- 不要说“支持所有页面/所有框架”——表格勾选、iframe、Canvas、文件上传目前不支持。
- 不要说“VLM 输出置信度并用于判定”——置信度已废弃，不参与判定。
- 不要说“源码是 AI 解析的”——源码是规则分析，需求文档才用 LLM。
- 不要把“增量分析”当现有功能——已经移除。
