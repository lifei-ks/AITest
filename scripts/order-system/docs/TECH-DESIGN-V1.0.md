## 1 需求背景

### 1.1 业务背景

测试平台 AICase 的链路是：读懂需求文档与源码，抽取测试点，再驱动浏览器跑通。这条链路要可信，前提是有个业务规则真实、可反复重置的被测对象。

一期之前使用的靶站 demo_site 只有 3 个静态页面，没有表单、没有业务规则、没有后端接口，只能覆盖页面元素类用例，业务规则类用例无从谈起。

于是本期建设 order-system：一个订单管理业务系统，覆盖表单录入、列表筛选、订单生命周期、接口契约与错误码，规模控制在可手工核对的程度。

选订单域作题材，是因为它天然盖住三类最常见的测试规则：字段约束、生命周期推进、条件筛选。题材越普通，用例越可复用。

### 1.2 一期目标

- 提供一条完整的业务主链路：录单 → 查单 → 推进订单生命周期
- 每条业务规则都在页面上有可观察的反馈文案，可做断言
- 保留接口层能力，让接口类用例与界面类用例都有落点
- 数据基线确定、可重置，两次执行互不干扰

## 2 已实现功能

### 2.1 能力清单

以下列出本期交付的全部可观察行为。

- 打开订单列表页，展示共 4 条订单，按创建时间倒序，待支付订单排第一行
- 顶部导航提供订单列表与新建订单两个菜单项，点击切换页面并高亮当前项
- 列表页关键字输入框的 placeholder 为「请输入订单号或收货人」，支持按订单号或收货人做包含匹配
- 状态筛选下拉框提供 6 个选项：待支付、已支付、已发货、已完成、已取消、已退款
- 选择已支付并点查询，列表只留下已支付订单，总数文案随之变化
- 点重置清空关键字与筛选状态，列表恢复 4 条种子订单
- 列表分页默认每页 10 条，可选 10、20、50，页脚显示总数、页大小与页码
- 待支付订单的操作列显示支付与取消两个按钮
- 已支付订单的操作列显示发货与退款两个按钮
- 已发货订单的操作列显示完成按钮
- 已完成、已取消、已退款的订单，操作列只显示 —，不渲染任何按钮
- 点支付按钮，订单状态由待支付变为已支付，提示支付成功
- 点发货按钮，订单状态由已支付变为已发货，提示发货成功
- 点完成按钮，订单状态由已发货变为已完成，提示订单已完成
- 点取消按钮，订单状态由待支付变为已取消，提示订单已取消
- 点退款按钮，订单状态由已支付变为已退款，提示退款成功
- 新建订单页表单含收货人、手机号、收货地址、订单金额、备注 5 个字段，其中备注为选填
- 提交合法数据后提示订单创建成功，自动跳转列表页，新订单出现在第一行
- 空表单提交时出现收货人不能为空等必填提示，订单未被创建
- 手机号填 123 提交，提示手机号格式不正确
- 订单金额填 0 提交，提示订单金额必须大于0
- 收货人填 21 个字符提交，提示收货人不能超过20个字符
- 收货地址填 101 个字符提交，提示收货地址不能超过100个字符
- 备注填 201 个字符提交，提示备注不能超过200个字符
- 对已支付订单调用支付接口，返回当前状态不可支付，只有待支付订单可以支付
- 调用 POST /api/demo/reset，数据恢复为 4 条种子订单

### 2.2 交付边界

页面只有两个：列表页与新建页。订单详情、修改、删除三个能力已完成服务端实现与接口契约，但页面未提供入口，只能通过接口验证，属于本期有意留出的增量空间。

### 2.3 一期不做的事

| 不做的事 | 原因 |
|---|---|
| 账号体系与角色权限 | 一期聚焦业务规则，鉴权会掩盖真正的字段与流转逻辑 |
| 数据库持久化 | 要的是零依赖启动与毫秒级重置，重启丢数据是刻意行为 |
| 订单详情页、编辑页、删除入口 | 只留接口层能力，作为后续版本的增量空间 |
| 商品与库存、优惠券、支付网关对接 | 属于订单域的外围，一期不引入外部依赖 |
| 统计报表、导出 | 与主链路无关，且容易引入不必要的复杂度 |

## 3 系统设计

### 3.1 总体架构

前后端分离，开发态由 Vite 代理转发，避免跨域配置。

```
Browser
  │   http://127.0.0.1:5273
  ▼
Vite Dev Server (5273) ─── /api 代理 ───▶ Spring Boot (8080)
  │                                          │
  └─ Vue 3 + Element Plus                    ├─ Controller   参数绑定、Bean 校验、响应封装
                                             ├─ Service      状态机守卫、业务规则
                                             ├─ Repository   内存存储 + 种子数据
                                             └─ 异常收敛     全局处理器统一错误码
```

请求链路：用户在页面操作 → axios 实例（`src/api/request.js`）注入统一前缀与超时 → Vite 代理转 8080 → Controller 校验入参与业务 → Service 判定流转 → Repository 读写内存 → 统一信封 `{code,message,data}` 返回 → 前端拦截器判定 code 并弹提示。

### 3.2 技术选型

| 层面 | 选择 | 理由 |
|---|---|---|
| 后端框架 | Spring Boot 3.4.5 | 校验、异常处理、参数绑定都开箱可用，靶站不必自造轮子 |
| 校验 | Jakarta Bean Validation 注解 | 约束声明在实体上，静态分析能直接读到字段规则 |
| 前端框架 | Vue 3 组合式 API | 与 Element Plus 配套成熟，页面逻辑短 |
| UI 库 | Element Plus 2.9 | 表格、分页、表单校验、消息提示直接可用 |
| 构建 | Vite 6 | 启动快，代理配置三行 |
| 存储 | ConcurrentHashMap 内存 | 零依赖启动、可毫秒级重置；代价是不验证数据库约束类规则 |
| 状态机 | 守卫式 if 判断，不用状态机框架 | 流转被写成显式条件分支，代码可读、可静态分析；用配置驱动的状态机框架反而把规则藏进配置，不利于源码分析 |

### 3.3 后端分层

| 层 | 职责 | 代表类 |
|---|---|---|
| Controller | 路由、参数绑定、Bean 校验触发、信封封装 | OrderController、DemoController |
| Service | 业务规则与状态守卫，非法流转在此抛业务异常 | OrderServiceImpl |
| Repository | 内存存储、种子数据装载、条件过滤与分页、重置 | OrderRepository |
| Entity / DTO | 订单实体、状态枚举、创建与修改入参 | Order、OrderStatus、CreateOrderRequest、UpdateOrderRequest |
| Common | 统一响应、业务异常、全局异常处理、跨域与代理配置 | ApiResponse、GlobalExceptionHandler、WebConfig |

分层原则：Controller 不做业务判断，Service 不碰 HTTP 细节，Repository 只管数据。规则集中在 Service 一层，改规则只改一个文件。

### 3.4 数据模型

订单实体共 10 个字段，服务端约束与页面表单一致。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | Long | 主键 | 种子占 1001~1004，新建从 1005 起自增 |
| orderNo | String | 非空 | ORD 加毫秒时间戳，创建后不可改 |
| receiverName | String | 非空，≤20 字符 | 收货人 |
| phone | String | 非空，^1[3-9]\d{9}$ | 手机号 |
| address | String | 非空，≤100 字符 | 收货地址 |
| amount | BigDecimal | 非空，≥0.01 | 订单金额，两位小数展示 |
| remark | String | ≤200 字符，可为空 | 备注 |
| status | 枚举 | 默认 CREATED | 6 值枚举，不可经修改接口写入 |
| createTime | 时间 | 服务端生成 | 创建时间 |
| updateTime | 时间 | 服务端生成 | 每次保存刷新 |

派生字段 statusLabel：接口同时返回中文状态文案，前端直接渲染，不做二次映射，避免双端文案漂移。

### 3.5 状态机设计

#### 3.5.1 状态定义

| 枚举 | 中文文案 | 类型 |
|---|---|---|
| CREATED | 待支付 | 初始态 |
| PAID | 已支付 | 中间态 |
| SHIPPED | 已发货 | 中间态 |
| COMPLETED | 已完成 | 终态 |
| CANCELLED | 已取消 | 终态 |
| REFUNDED | 已退款 | 终态 |

#### 3.5.2 合法流转

| 编号 | 源态 | 动作 | 目标态 | 接口 | 成功提示 |
|---|---|---|---|---|---|
| T1 | 待支付 | 支付 | 已支付 | POST /api/orders/{id}/pay | 支付成功 |
| T2 | 待支付 | 取消 | 已取消 | POST /api/orders/{id}/cancel | 订单已取消 |
| T3 | 已支付 | 发货 | 已发货 | POST /api/orders/{id}/ship | 发货成功 |
| T4 | 已支付 | 退款 | 已退款 | POST /api/orders/{id}/refund | 退款成功 |
| T5 | 已发货 | 完成 | 已完成 | POST /api/orders/{id}/complete | 订单已完成 |

#### 3.5.3 非法流转矩阵

6 个状态 × 5 个动作共 30 格，标记为 ✗ 的组合必须被拒绝并给出对应提示。

| 当前状态 | 支付 | 发货 | 完成 | 取消 | 退款 |
|---|---|---|---|---|---|
| 待支付 | ✅ T1 | ✗ | ✗ | ✅ T2 | ✗ |
| 已支付 | ✗ | ✅ T3 | ✗ | ✗ | ✅ T4 |
| 已发货 | ✗ | ✗ | ✅ T5 | ✗ | ✗ |
| 已完成 | ✗ | ✗ | ✗ | ✗ | ✗ |
| 已取消 | ✗ | ✗ | ✗ | ✗ | ✗ |
| 已退款 | ✗ | ✗ | ✗ | ✗ | ✗ |

非法流转的提示文案按动作区分：

| 动作 | 提示文案 |
|---|---|
| 支付 | 当前状态不可支付，只有待支付订单可以支付 |
| 发货 | 当前状态不可发货，只有已支付订单可以发货 |
| 完成 | 当前状态不可完成，只有已发货订单可以完成 |
| 取消 | 当前状态不可取消，只有待支付订单可以取消 |
| 退款 | 当前状态不可退款，只有已支付订单可以退款 |

#### 3.5.4 实现方式

每个动作方法开头做一次前置守卫，不满足源态立即抛出业务异常，通过后才写状态：

```
pay:      requireStatus(order, CREATED, "支付")    → 置 PAID
cancel:   requireStatus(order, CREATED, "取消")    → 置 CANCELLED
ship:     requireStatus(order, PAID,    "发货")    → 置 SHIPPED
refund:   requireStatus(order, PAID,    "退款")    → 置 REFUNDED
complete: requireStatus(order, SHIPPED, "完成")    → 置 COMPLETED
```

守卫式实现的好处是规则完全线性可读，每个动作只认一个源态，不存在隐式转移路径；代价是动作增多时守卫代码会重复，到二期动作超过 8 个时应重构为流转表。

#### 3.5.5 修改权限

修改接口只接受收货人、手机号、收货地址、备注四个字段，`UpdateOrderRequest` 里刻意不含 status，从类型层面封死越权改状态。

已完成、已取消的订单不允许修改，提示「已完成或已取消的订单不能修改」。删除接口可删除任意存在的订单。

### 3.6 接口设计

#### 3.6.1 统一响应与错误码

所有接口返回同一信封 `{code, message, data}`，成功时 code 为 0、message 为 ok。

| code | 含义 | HTTP | 页面表现 |
|---|---|---|---|
| 0 | 成功 | 200 | 按接口成功行为处理 |
| 40000 | 参数校验失败 | 400 | 弹窗展示 message |
| 40001 | 业务规则不满足 | 400 | 弹窗展示 message |
| 40401 | 订单不存在 | 400 | 弹窗展示「订单不存在」 |
| 50000 | 服务端异常 | 500 | 弹窗展示「服务器内部错误」 |

#### 3.6.2 接口清单

| 编号 | 接口 | 入参 | 成功返回 data | 页面入口 |
|---|---|---|---|---|
| A1 | POST /api/orders | receiverName、phone、address、amount、remark | 新建订单，状态 CREATED | 有（新建页） |
| A2 | GET /api/orders | page、pageSize、status、keyword | total、page、pageSize、items | 有（列表页） |
| A3 | GET /api/orders/status-options | 无 | 6 个状态选项，含 value 与 label | 有（下拉框） |
| A4 | GET /api/orders/{id} | 路径 id | 单个订单 | 无 |
| A5 | PUT /api/orders/{id} | receiverName、phone、address、remark | 修改后的订单 | 无 |
| A6 | DELETE /api/orders/{id} | 路径 id | 空 | 无 |
| A7 | POST /api/orders/{id}/pay | 路径 id | 状态 PAID 的订单 | 有（行内按钮） |
| A8 | POST /api/orders/{id}/ship | 路径 id | 状态 SHIPPED 的订单 | 有（行内按钮） |
| A9 | POST /api/orders/{id}/complete | 路径 id | 状态 COMPLETED 的订单 | 有（行内按钮） |
| A10 | POST /api/orders/{id}/cancel | 路径 id | 状态 CANCELLED 的订单 | 有（行内按钮） |
| A11 | POST /api/orders/{id}/refund | 路径 id | 状态 REFUNDED 的订单 | 有（行内按钮） |
| A12 | POST /api/demo/reset | 无 | 当前订单总数，值为 4 | 无（测试钩子） |

#### 3.6.3 分页与筛选语义

| 参数 | 默认 | 语义 | 边界 |
|---|---|---|---|
| page | 1 | 页码，从 1 开始 | 传 0 或负数等价于第 1 页 |
| pageSize | 10 | 每页条数 | 未做上限校验，传极大值返回全部 |
| status | 空 | 只接受枚举名（CREATED 等） | 传中文标签不生效，等价于不筛选 |
| keyword | 空 | 订单号或收货人包含匹配，忽略大小写与首尾空格 | 不匹配手机号与收货地址 |

页码超出总页数时返回空数组，不报错；total 为筛选后的总条数，与分页无关。点查询按钮时前端先把页码重置为 1，避免在第 3 页筛选后落到空页。

### 3.7 前端设计

#### 3.7.1 路由

| 路由 | 页面 | 标题 |
|---|---|---|
| /orders/list | 订单列表 | 订单列表 - 订单管理系统 |
| /orders/create | 新建订单 | 新建订单 - 订单管理系统 |
| / | 重定向到列表 | — |

#### 3.7.2 请求与提示

axios 实例统一注入 `/api` 前缀与超时；响应拦截器判定 code，非 0 时统一弹错并 reject，页面 `catch` 块只写注释、不重复提示，避免双重弹窗。

#### 3.7.3 表单校验

| 字段 | 控件 | placeholder | 前端规则 | 提示 |
|---|---|---|---|---|
| 收货人 | el-input | 请输入收货人 | 必填，≤20 字符 | 收货人不能为空 / 收货人不能超过20个字符 |
| 手机号 | el-input | 请输入手机号 | 必填，^1[3-9]\d{9}$ | 手机号不能为空 / 手机号格式不正确 |
| 收货地址 | el-input | 请输入收货地址 | 必填，≤100 字符 | 收货地址不能为空 / 收货地址不能超过100个字符 |
| 订单金额 | el-input | 请输入订单金额 | 必填 | 订单金额不能为空 / 订单金额必须大于0 |
| 备注 | el-input textarea 3 行 | 请输入备注（选填） | ≤200 字符 | 备注不能超过200个字符 |

双端校验强度只有金额一处不一致：前端只做必填，没有数值与下限判断，所以金额填 0 会被前端放行、由服务端拦截并回「订单金额必须大于0」；金额填非数字则在服务端反序列化阶段失败，回「服务器内部错误」。这一处不一致是刻意留下的，用来验证执行器能否区分前端校验与服务端校验。

提交按钮在请求期间进入 loading 态防重复提交；成功后提示「订单创建成功」并跳转列表，失败时停留当前页。

#### 3.7.4 列表页交互

行内按钮按 `row.status` 条件渲染，不满足状态时按钮节点根本不存在（不是置灰），因此断言应指向「按钮消失」而不是「按钮禁用」。操作成功后重新拉取当前页，状态标签与可用按钮同步刷新。

### 3.8 异常处理设计

| 异常类型 | 处理 | 返回 |
|---|---|---|
| MethodArgumentNotValidException | 取绑定结果中的字段错误 | 40000 + 字段提示文案 |
| BusinessException | 业务规则不满足 | 40001 + 自定义文案 |
| 订单查询为空 | Service 抛业务异常 | 40401 + 「订单不存在」 |
| 其他 Exception | 兜底捕获，日志记录 | 50000 + 「服务器内部错误」 |

服务端一次只返回一条字段提示：多字段同时非法时，具体返回哪一条由校验器顺序决定，不保证是页面上从上到下的第一个字段。实测空表单提交返回的是「收货地址不能为空」。

### 3.9 存储与重置设计

数据存 `ConcurrentHashMap<Long, Order>`，启动时装载 4 条种子订单，id 从 1001 到 1004。重置接口清空后重新装载种子，返回总数 4。

重置是靶站的关键能力：每次执行前调一次，就能保证数据基线确定，避免用例之间互相污染。副作用是重启会丢掉新建订单，任何断言都不该假设上次执行的数据还在。

### 4.1 种子数据

| 1002 | ORD20260101002 | 李四 | 13800000002 | 88.50 | 已支付 | 第 2 行 |

| 1004 | ORD20260101004 | 赵六 | 13800000004 | 45.00 | 已完成 | 第 4 行 |

重置后总数文案为「共 4 条订单」。种子数据不含已取消与已退款订单，这两类状态只能通过页面操作产生。

### 4.3 影响断言写法的实现细节

**① 两字中文按钮会被渲染出空格。** Element Plus 默认在两个汉字之间插空格，页面上「支付」的实际可见文本是「支 付」，「完成」是「完 成」，「发货」是「发 货」，「取消」是「取 消」，「退款」是「退 款」，「查询」是「查 询」，「重置」是「重 置」。文本选择器不能用 `//button[text()='支付']`，必须用 `//button[normalize-space(.)='支付']`。三个字以上的按钮（新建订单、提交订单、返回列表）不受影响。

**② 终态订单没有可点击按钮。** 已完成、已取消、已退款的订单操作列只有 —，针对它们的断言应指向「无按钮」与状态标签文案。

**③ 筛选走查询参数。** 条件由前端拼接、后端在内存中全量过滤后分页，筛选与分页可组合，页码切换不影响筛选条件。

**④ 无登录与权限体系。** 系统没有登录页、没有角色差异，权限类用例不适用。

## 6 已知限制

| 编号 | 限制 | 影响 |
|---|---|---|
| L1 | 金额传非数字返回 50000 而非友好提示 | 用例应断言「服务器内部错误」，不要期待字段级文案 |
| L2 | 多字段非法只回一条提示，顺序不确定 | 多字段用例断言「出现字段提示」这一事实，或拆成单字段用例 |
| L3 | 已退款订单仍可经修改接口改收货信息 | 修改拦截只覆盖已完成与已取消，与终态不可变的语义不一致 |
| L4 | pageSize 无上限 | 传极大值返回全表，分页边界用例可据此设计 |
| L5 | 修改与删除无页面入口 | 只能接口验证，不能生成 UI 用例 |
| L6 | 数据在内存，重启即回到种子 | 不要假设跨次执行的数据留存 |
